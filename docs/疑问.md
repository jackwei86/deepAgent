# DeepAgent 常见疑问解答

> 更新：2026-09-10　　背景：图像美颜链路已在 Open WebUI + DeepSeek + C++ SDK 上全链路打通

## 1. 作为附件的图片信息会发送到 DeepSeek 消耗流量吗？

**会。** 当前给 `deepseek-v4-pro` 开启了 Vision（关闭则前端拦截图片上传），Open WebUI 会把图片转成 base64 塞进发给 DeepSeek 的请求里。v4-pro 是文本模型，DeepSeek 收到后直接丢弃并替换为占位文本——**图片数据走了网络但没被模型利用**，且多轮对话中每次请求可能重复携带。

如果在意流量，两条路：

1. 使用素材库路径方案（见问题 5，推荐）——图片完全不经过 DeepSeek；
2. 视觉场景换 `deepseek-v4-flash-vision-exp`（图片被真正利用，但该模型不在官方 `/models` 列表，需手动配置连接的模型 ID 列表）。

## 2. 美颜的命令是如何识别并如何实现调用 C++ beauty SDK 的？

核心是"**LLM 出意图，Python 出命令行，C++ 出算法**"：

1. **工具注册**：4 个工具函数的中文 docstring + 参数签名被 Open WebUI 转成 JSON Schema，作为 `tools` 参数随请求发给 DeepSeek（function calling）；
2. **意图识别**：模型从用户话语中匹配到"美颜"意图，返回 `image_beauty(strength=0.8)` 调用；
3. **任务执行**：Open WebUI 回调 Python 工具函数 → 定位附件（三级回退：顶层 `__files__` → 消息内 `files` → 消息 content 中的 image_url 部件）→ 生成任务单 JSON（`data/tasks/<task_id>/task.json`）→ `subprocess` 执行 `deepagent-cv.exe run --task task.json`；
4. **进度与结果**：C++ CLI 逐行输出 JSON-lines 进度事件 → Python 解析后经 `event_emitter` 推给 UI 状态条；完成后产物上传文件库并通过 `files` 事件挂到消息上原生预览。

## 3. 后续如果要新增 C++ 工具，如何添加？

| 层 | 要做的事 |
|---|---|
| C++ | 在 `cpp-sdk` 加算法函数（照 `ProgressReporter` 模式写进度回调），CLI 加新子命令 + 任务单类型分支（`TaskSpec`/`spec_from_task_json`/`execute_spec`），`scripts\build_windows.bat` 重编 |
| Python | 在 `assistant\tools\` 复制一个现有工具文件改名（中文 docstring 就是给 LLM 的说明书），修改 `task_type` / `sdk_command` / 参数 |
| 注册 | `python assistant\install_tools.py --token <管理员API密钥>`，然后在模型编辑页勾选新工具（或聊天内工具开关） |

`task_manager` / `sdk_runner` / 任务单流程均为通用实现，无需改动；`docs\任务信息JSON格式.md` 的类型枚举同步补一行。

## 4. 使用截图作为附件的图片是否还能正常运行获取输出？

**能。** 对处理管线而言截图就是普通 PNG/JPG，OpenCV 直接解码，不关心图片来源（截图工具存盘后上传、或 Ctrl+V 直接粘贴进输入框均可，走同一上传流程）。

提示：超高分屏截图（4K+）滤波时自动降到 1280 工作分辨率加速、输出仍还原原始尺寸；支持格式为 OpenCV 可解码的 jpg/png/bmp/webp 等。

## 5. 处理视频会先发到 DeepSeek 吗？是否适合用专门的素材库文件夹替代附件？

**视频不会发到 DeepSeek**——只有图片作为视觉内容进入请求，视频始终留在本地由工具直接读取，不消耗接口流量。

**素材库方案已采纳并实现（v1.1.0）**：目录为 `media/<登录用户名>/image|video`，
对话中说"素材库 / 收藏夹 / 当前目录"即指该目录。收益已落地：

- 图片彻底不经过 DeepSeek（省流量，也消除"不支持的图片"占位符问题）；
- 没有附件大小限制，大视频免去上传等待；
- 便于批量处理和第三方工具直接复用文件（任务单 `inputs[].path` 天然路径寻址）。

使用方式：把文件放入素材库（网页 `/media-ui/` 上传，或直接拷贝进目录），
然后说 *"处理素材库里的 photo.jpg，磨皮强一点"* 即可，无需上传附件。

## 6. 能否将整个程序改为 Windows Electron 客户端 + 任务栏托盘程序作为服务端？

**可以，且不需要改动现有后端。** Open WebUI 本身就是本地 Web 服务（127.0.0.1:8080），桌面化只是换壳：

- **托盘服务端**：`pythonw + pystray` 小脚本（或 Electron 主进程直接托管），负责启动/停止 `open-webui serve`、开机自启、托盘菜单（打开界面/退出）；
- **Electron 客户端**：`BrowserWindow` 加载 `http://127.0.0.1:8080`，关闭窗口最小化到托盘，`electron-builder` 打包安装包；
- **更轻的替代**：只要"独立窗口 + 托盘"体验，Edge/Chrome"安装为应用"（PWA）零开发即可；Tauri 打包体积比 Electron 小一个数量级。

工作量估计半天到一天（托盘脚本 + Electron 壳 + 打包配置）。

## 7. LLM 返回结果后，Open WebUI 的处理步骤是固定的吗？LangGraph 能自定义吗？（2026-09-11）

**理解基本正确，两点补充：**

当前固定管线：LLM 流式返回 → 推理内容折叠 → 工具调用循环（有工具则执行并把结果回传模型再答）→ 引用/状态事件 → 最终渲染。这条主流程写死在 Open WebUI 中间件里，使用期间不会变。

Open WebUI 并非零扩展点：Filters 的 outlet 可后处理最终回复文本；Pipe 可把任意代码包装成"模型"执行体。但**工具循环的组织方式**（执行几次、什么条件分支、失败重试几次、是否人工审批）确实无法自定义。

LangGraph 的正确定位：把"返回结果之后做什么"从固定管线变成你编写的图——条件分支、循环重试、并行节点、interrupt 人工审批、按 checkpoint 回退全部可编程。代价：聊天编排循环要搬进图里，Open WebUI 退化为 UI 外壳（折中方案：用 Pipe 把图包装成一个自定义"模型"），以及《任务链与版本树-二期LangGraph方案.md》中评估的双真相源与版本耦合问题。

注意：当前 4 个工具本身就是在"LLM 返回工具调用后"执行的自定义代码——自定义"做什么"已经实现；LangGraph 改变的是"多步编排与状态管理"的组织方式。

## 8. Open WebUI 调用本地 4 种工具的原理确认（2026-09-11）

**理解完全正确**，完整链路四步：

1. **能力声明**：工具注册时，Open WebUI 把 4 个工具函数的 docstring+参数签名转成 JSON Schema（名称/描述/参数），作为 `tools` 数组随用户输入一起发给 LLM；
2. **LLM 决策**：DeepSeek 分析用户输入，从 4 个工具中选出匹配项，返回 `tool_calls`（工具名 + 参数 JSON）——**LLM 只决策、只点菜，不执行任何东西，也不调用远端处理能力**；
3. **本地执行**：Open WebUI 按 tool_calls 调用我们注册的 Python 工具函数（function call with args，运行在 Open WebUI 进程内）→ 生成任务单 JSON → `subprocess` 命令行执行本地 C++ SDK（deepagent-cv.exe）；
4. **结果回传**：工具返回的文本作为 tool 结果再喂给 LLM 组织最终回复；产物通过 files 事件挂到消息上预览。

两个精确化：① 执行者 = 本地 Open WebUI 进程 + C++ 子进程，LLM 看不到也碰不到图片本身；② 工具的 schema 描述文本会消耗少量 token，但图片/视频素材文件不发往 LLM 服务商（见疑问 1、5）。
